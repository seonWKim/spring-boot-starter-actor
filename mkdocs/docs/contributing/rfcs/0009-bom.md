# RFC 0009: Publish a bill of materials

From row 14 of the [Spring conventions comparison](../spring-conventions.md).

## Status

Proposed

## Problem

The project publishes three artifacts (`spring-boot-starter-actor`, `spring-boot-starter-actor_3`,
`spring-boot-starter-actor-metrics`), with more coming ([RFC 0007](0007-test-artifact.md)). Users repeat the
version on each and can mix versions by mistake. Spring Cloud, Micrometer, Resilience4j, Temporal and Pekko
each publish a BOM.

## Proposal

1. New Gradle module `bom`, using the `java-platform` plugin, published as `spring-boot-starter-actor-bom`.
2. It lists every published artifact at the project version. It does not list Pekko or Spring Boot: Boot users
   already import Boot's BOM, and forcing Pekko versions belongs in the starter's own `api` dependencies.
3. Usage:

    ```kotlin
    dependencies {
        implementation(platform("io.github.seonwkim:spring-boot-starter-actor-bom:0.11.0"))
        implementation("io.github.seonwkim:spring-boot-starter-actor")
        implementation("io.github.seonwkim:spring-boot-starter-actor-metrics")
    }
    ```

## Alternatives considered

- **Do nothing.** Fine while there are two artifacts per app.
- **Include Pekko in the BOM.** Would pin Pekko versions for apps that also use Pekko directly; users can
  import `pekko-bom_3` themselves.

## Risks and rollout

- The publish workflow must publish the BOM in the same release as the other artifacts.
- `com.vanniktech.maven.publish` supports `java-platform`; packaging must be `pom`, not `jar`, so the
  root build's `packaging = "jar"` must be skipped for this module.

## Files it would change

- `settings.gradle.kts`
- `gradle.properties` (artifact id, pom name and description)
- `build.gradle.kts` (skip `java`/`java-library` for the `bom` module, set packaging)
- `bom/build.gradle.kts` (new)
- `mkdocs/docs/getting-started.md`
