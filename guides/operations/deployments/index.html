    Deployments

    This guide covers how to release a new version of a clustered actor application without failing requests: rolling updates, canary releases and blue-green switches, and how to change messages so that two versions can run side by side.

    The commands come from the Kubernetes example (example/kubernetes), which runs the chat example as a three-pod cluster on a local kind cluster. The ideas apply to any platform.

    Choosing a strategy

    Strategy What runs Traffic Versions mix in one cluster Script
    Rolling update One cluster; old and new pods side by side during the rollout Moves pod by pod Yes kubectl set image
    Canary One cluster; a few new pods join the running cluster Share = canary pods / all pods Yes scripts/canary.sh
    Blue-green Two separate clusters (blue and green) Switches in one step No scripts/blue-green.sh
    • Use a rolling update for most releases. It needs no extra capacity beyond one pod.
    • Use a canary when you want a few real requests on the new version first, with a quick way back.
    • Use blue-green when the new version cannot talk to the old one (an incompatible message change) or when you want to switch all traffic at once. It needs twice the pods for a while, and in-memory state does not move.

    All three rely on the graceful shutdown settings: each old pod leaves the cluster on purpose, so its sharded entities and singletons move instead of waiting for the split brain resolver.

    Rolling update

    A rolling update replaces pods one at a time inside one cluster. The example's Deployment adds a new pod before it removes an old one, so the cluster never drops below its size:

    spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0    # never fewer than 3 ready pods
      maxSurge: 1          # start one new pod before stopping an old one

    Each new pod joins the running cluster. Its readiness probe includes actorCluster, so it gets traffic only once it is an Up member (see Health checks). Then Kubernetes stops an old pod: the preStop sleep lets the load balancer drop it, and coordinated shutdown moves its entities to the other nodes.

    kubectl set image deployment/spring-actor spring-actor=spring-actor-chat:v2 -n spring-actor
kubectl rollout status deployment/spring-actor -n spring-actor

# Go back to the previous version
kubectl rollout undo deployment/spring-actor -n spring-actor

    Canary

    A canary runs a few pods of the new version in the same cluster as the main pods. canary.sh start copies the live Deployment as spring-actor-canary with the new image and a track: canary label. The Services select app=spring-actor, so they send the canary pods their share of the requests: with three main pods and one canary, about one in four.

    cd example/kubernetes
scripts/canary.sh start spring-actor-chat:v3      # one canary pod; `start <image> 2` for two
scripts/canary.sh promote                         # roll the main pods to v3, then remove the canary
# scripts/canary.sh abort                         # or remove the canary and keep the main pods as they are

    Because the canary is a member of the same cluster, sharded entities can move to it and it exchanges messages with the old pods. Both versions must read each other's messages and entity state (see Message compatibility).

    Blue-green

    Blue-green starts the new version as a second, separate cluster. blue-green.sh deploy copies the live Deployment as spring-actor-green with the new image, labels its pods app=spring-actor-green, and points its Kubernetes API discovery at that label (--spring.actor.pekko.discovery.kubernetes-api.pod-label-selector=app=spring-actor-green). So green forms its own cluster and never exchanges messages with blue.

    Before green starts, deploy also copies each NetworkPolicy that selects app=spring-actor (for example spring-actor-green from spring-actor, and spring-actor-green-store from spring-actor-store in the discovery overlays), with every app=spring-actor selector changed to app=spring-actor-green. Green gets the same restrictions as blue, and remoting (25520) and management (7626) open only between pods of the same color: blue and green cannot reach each other's cluster ports. A canary keeps app=spring-actor, so blue's policies cover it.

    The release pipeline

    A blue-green release runs in four stages. Each one waits for a signal before the next starts:

    Stage Command Waits for
    1. Warm up blue-green.sh deploy <image> every green pod answers UP on /actuator/health/warmup, then is ready
    2. Activate blue-green.sh activate the generation endpoint accepts green; then the HTTP Service's selector picks the green pods
    3. Verify blue-green.sh verify the generation record says green, and the Service's ready endpoints are exactly the green pods
    4. Retire blue-green.sh retire run it once green has served for a while; it deletes blue 
    cd example/kubernetes
scripts/blue-green.sh deploy spring-actor-chat:v4   # start green beside blue and wait until it is warm
scripts/blue-green.sh activate                      # green becomes the active generation; the Service selects it
scripts/blue-green.sh verify                        # wait until only green pods serve
# scripts/blue-green.sh rollback                    # activate blue again (a new epoch) and select it
scripts/blue-green.sh retire                        # delete blue

    The first stage gates on warm-up, not on kubectl rollout status or the Deployment's Available condition. Those follow traffic readiness, and in a pipeline where the standby color refuses traffic until it is activated they never come. The warm-up group says only that the pod can be activated:

    • the pod is an Up member of its cluster,
    • the cluster has at least management.health.actor.warmup.min-members Up members (the example sets 2),
    • and the discovery store answers, when the cluster forms through jdbc or redis discovery.

    It never depends on which color is active. The three probes stay apart: liveness says whether to restart the pod, readiness whether to send it traffic, and warm-up whether it can be activated (see Health checks).

    In-memory state does not move: entities, singletons and topics start empty on green. Keep state that must survive the switch in a database or event journal both clusters read (State in a Database, Event-Sourced Actors). Until retire, rollback sends traffic back to blue, which still has its state.

    The active generation

    Which color is active is a record in the store the cluster already uses (Redis or the database), not only a Service selector. Each record is a generation: a color, an epoch that grows by one with every activation, the deployment operation ID that activated it, and when. The application can read it, and the pipeline changes it only through a compare-and-set:

    • Competing deploys fail loudly. An activation names the epoch it expects to be active. If another deploy activated in between, it is rejected (EPOCH_MISMATCH, HTTP 409) and nothing changes. Of several activations that expect the same epoch, exactly one wins.
    • Retries are idempotent. An activation carries an operation ID. Retrying it with the same color and expected epoch returns the generation it activated the first time (ALREADY_ACTIVATED, HTTP 200), even after the epoch has moved on. The same operation ID with another color or epoch is OPERATION_CONFLICT (409). A pipeline keeps the expected epoch and the operation ID it used, and sends both again when it retries.
    • Old work stays fenced. Blue, then green, then blue again gives epochs 1, 2 and 3. Work that blue stamped in its first turn carries epoch 1 and is refused in its second (epoch 3), because the epoch never goes back.

    Turn it on in each color with its color and a store:

    spring:
  actor:
    generation:
      color: blue          # green in the other deployment
      store: redis         # jdbc: the actor_generation table; custom: your GenerationStore bean
      # name: orders       # the record both colors share; default: spring.actor.name
      # refresh: 1s        # how long a node reuses a read of the record
management:
  endpoints:
    web:
      exposure:
        include: health,generation
  endpoint:
    generation:
      access: unrestricted   # activation is a write: read-only by default

    The generation endpoint. GET /actuator/generation returns this node's color and the active generation. POST /actuator/generation with color, expectedEpoch (0 before the first activation) and operationId activates a color:

    curl -u deployer:$PASSWORD -X POST localhost:8080/actuator/generation \
  -H 'Content-Type: application/json' \
  -d '{"color":"green","expectedEpoch":1,"operationId":"release-2026-11-11-1"}'
# {"outcome":"ACTIVATED","generation":{"color":"green","epoch":2,"operationId":"release-2026-11-11-1",...}}

    Activation needs an authenticated user: a request without one is answered 401 (UNAUTHENTICATED). Secure the endpoint with Spring Security like any other write endpoint, for example with a role:

    @Bean
SecurityFilterChain actuator(HttpSecurity http) throws Exception {
    return http.securityMatcher(EndpointRequest.to("generation"))
            .authorizeHttpRequests(requests -> requests
                    .requestMatchers(HttpMethod.POST).hasRole("DEPLOYER")
                    .anyRequest().permitAll())
            .httpBasic(Customizer.withDefaults())
            .csrf(csrf -> csrf.disable()) // called by a pipeline, not a browser session
            .build();
}

    @Bean
fun actuator(http: HttpSecurity): SecurityFilterChain =
    http.securityMatcher(EndpointRequest.to("generation"))
        .authorizeHttpRequests {
            it.requestMatchers(HttpMethod.POST).hasRole("DEPLOYER")
                .anyRequest().permitAll()
        }
        .httpBasic(Customizer.withDefaults())
        .csrf { it.disable() } // called by a pipeline, not a browser session
        .build()

    Audit. Every attempt that reaches the endpoint, or DeploymentGeneration.activate in your code, publishes an ActivationEvent (an ApplicationEvent) with the requested color, expected epoch, operation ID, the user's name and the result. The starter also logs it (INFO when accepted, WARN when rejected) and counts it in actor.generation.activations, tagged with outcome. A request that Spring Security turns away never reaches the endpoint, so it shows in Spring Security's events instead.

    Fencing in your code. Inject DeploymentGeneration. Stamp work with stamp() where it starts (it fails when this node's color is not active), and check(epoch) it where it runs. A stale epoch throws StaleGenerationException, the retryable outcome of reliable delivery:

    long epoch = generation.stamp();                       // where the work starts
sender.send(new ChargeOrder(orderId, epoch), key);

.onMessage(ChargeOrder.class, (ctx, msg) -> {
    generation.check(msg.epoch());                     // StaleGenerationException if it is old
    payments.charge(msg.orderId());
    return SpringActorBehavior.same();
})

    val epoch = generation.stamp()                         // where the work starts
sender.send(ChargeOrder(orderId, epoch), key)

.onMessage(ChargeOrder::class.java) { _, msg ->
    generation.check(msg.epoch)                        // StaleGenerationException if it is old
    payments.charge(msg.orderId)
    SpringActorBehavior.same()
}

    A node reuses a read of the record for spring.actor.generation.refresh (1 second), so for up to that long after an activation elsewhere it still accepts the old epoch. Where that matters, keep the epoch with the data and compare it in the write itself (UPDATE ... WHERE epoch <= ?).

    Stores. jdbc keeps one row per activation in actor_generation (created with the other actor-jdbc tables): the primary key on deployment and epoch is the compare-and-set. redis keeps the record and the operation IDs in two hashes and changes them in one Lua script. Redis replicates asynchronously, so a failover can lose an activation it had just accepted; use jdbc where that is not acceptable. Your own GenerationStore bean replaces both, and must pass GenerationStoreContract from actor-test.

    Requests at the cutover

    In the example the Service selector switches the colors, and readiness does not depend on the color. So deploy waits for warm-up and then for the green pods to be ready. Warm-up alone is not enough there: a pod can be warm before its readiness probe first passes (the example's probe starts after 30 seconds), and a Service that selects only pods that are not ready yet has no endpoints. Measured on kind with test-strategies.sh (four workers asking sharded entities):

    deploy waited for Requests Failed Service served only green
    warm-up only 15,057 20, all within 10 seconds after activate 15 seconds after activate
    warm-up, then ready (the script today) 23,151 and 22,890 (two runs) 0 and 0 at the first check after activate

    Blue keeps running and serving until retire, so a node whose proxy rules still point at blue for a moment after the switch still gets answers.

    When readiness itself switches the colors (the standby refuses traffic until it is activated, and one Service selects both), the cutover waits for readiness to propagate: each pod's readiness probe has to pass (periodSeconds times successThreshold for the new color, periodSeconds times failureThreshold for the old one), then the endpoint controller and every node's kube-proxy update. Shorter probe intervals shorten that window but don't close it: requests routed during it reach a pod that is about to leave or none at all. This mode was not measured here. Close the window with draining instead:

    • switch with the Service selector (or another routing change) while both colors are ready, and keep the old pods running until verify shows the Service no longer selects them (retire comes last);
    • the preStop sleep (10 seconds in the example) keeps a terminating pod serving while the endpoint removal propagates;
    • server.shutdown: graceful finishes the requests the pod has already accepted.

    scripts/test-strategies.sh prints, for the blue-green step, how long the Service took to serve only green and how many requests failed from activation on.

    Testing the strategies under load

    scripts/test-strategies.sh runs all three strategies on the kind cluster from setup-local.sh while scripts/load.sh sends requests, and fails if any request failed:

    cd example/kubernetes
./setup-local.sh
scripts/test-strategies.sh
# rolling        total=... ok=... failed=0 ok
# canary         total=... ok=... failed=0 ok
# blue-green     total=... ok=... failed=0 ok

    It runs, in order: a rolling update to v2 (120 seconds of load), a canary of v3 that is then promoted (180 seconds), and a blue-green release of v4 through the four stages above (90 seconds, then retire). Each step's load runs four workers that ask sharded entities (/hello?message=hi&entityId=e<0-49>).

    What it checks and what it does not:

    • load.sh counts a request as ok only when the actor replied. The chat app answers 200 with Request timed out ... when an ask fails, so the HTTP status alone would hide lost messages.
    • The new versions are retags of the same image, so it checks the rollout mechanics (joining, leaving, entities moving, the Service switching), not a change in the code.

    Message compatibility across versions

    Rolling updates and canaries mix versions in one cluster. Old and new pods exchange messages, and a sharded entity can move from an old pod to a new one. Every message and every piece of entity state that crosses nodes must be readable by both versions:

    • Add fields as optional. The old version must accept a message with the new field, and the new version a message without it.
    • Don't rename or remove fields or message types in the same release.
    • Keep each type on the same serializer (JsonSerializable or CborSerializable).
    • Make an incompatible change in two releases: first one that reads both formats, then one that writes the new format.

    For example, a second release adds an optional field to a command:

    // v1
public static class SayHello extends AskCommand<String> implements Command {
    public final String message;

    public SayHello(String message) {
        this.message = message;
    }
}

// v2: a new, optional field. Messages from v1 nodes don't have it.
public static class SayHello extends AskCommand<String> implements Command {
    public final String message;
    @Nullable public final String language;

    public SayHello(String message, @Nullable String language) {
        this.message = message;
        this.language = language;
    }
}

    // v1
class SayHello(val message: String) : AskCommand<String>(), Command

// v2: a new, optional field. Messages from v1 nodes don't have it.
class SayHello(val message: String, val language: String? = null) : AskCommand<String>(), Command

    The starter's build checks this on every change: MixedVersionMessageTest runs two nodes in one JVM, one with a message class and one with the same class plus a field, and sends a message each way between sharded entities. The old node reads the new message and ignores the field it doesn't know; the new node reads the old message with the missing field as null. The test covers JsonSerializable messages with the starter's default Jackson settings. It does not cover a renamed or removed field, a renamed class, or stored events and snapshots. To run the same check on your own messages, see Two versions of a message in one cluster.

    On Kubernetes, this was also measured on kind with a canary of the chat app: adding a field to SayHello lost no requests (28,842 of 28,842), while renaming the class lost 104 of 7,105, which timed out because the old nodes could not read the new type.

    Blue-green never mixes versions. The two clusters never exchange messages, so the message format can change freely. Stored state is different: events and snapshots in a journal or database must still be readable by the new version (see Event-Sourced Actors).

    Rollback

    Strategy How to go back
    Rolling update kubectl rollout undo deployment/spring-actor -n spring-actor: a rolling update in the other direction, so the same compatibility rules apply
    Canary scripts/canary.sh abort removes the canary pods; the main pods were never changed
    Blue-green scripts/blue-green.sh rollback until retire; blue still has its in-memory state
