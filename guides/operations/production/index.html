    Running in Production

    This guide covers what matters when you run an actor application in production, for example on Kubernetes: how it shuts down without losing work, how health checks report the actor system and the cluster, a checklist to go through before the first release, and GraalVM native images.

    For metrics, tracing and alerts, see Monitoring. For rolling, canary and blue-green releases, see Deployments.

    Graceful shutdown

    When the Spring application context closes (on SIGTERM, or when you call context.close()), the starter shuts the actor system down through Pekko coordinated shutdown. In cluster mode the node leaves the cluster on purpose: other nodes see it go Leaving → Exiting → Removed, sharded entities and cluster singletons move to the remaining nodes, and the node is never reported as unreachable or downed by the split brain resolver.

    Shutdown order

    The starter registers a Spring SmartLifecycle bean, ActorSystemShutdownLifecycle, at phase ActorSystemShutdownLifecycle.PHASE (Integer.MAX_VALUE - 4096). Spring stops lifecycle beans from the highest phase to the lowest before it destroys any bean, so on shutdown:

    1. With server.shutdown=graceful, the web server stops accepting requests and drains in-flight ones (Spring Boot's web server lifecycles run at higher phases).
    2. The actor system runs coordinated shutdown and the starter waits for it to terminate, at most the configured timeout.
    3. Spring destroys the remaining beans, including the services, repositories and connection pools your actors use. Actors are already stopped, so they never call a destroyed bean.

    The wait is bounded: if an actor blocks shutdown (for example a handler stuck on blocking I/O), closing the context returns after the timeout with a warning in the log, and the process can exit instead of hanging.

    The shutdown runs once. If the actor system has already terminated, for example because the node was downed and Pekko shut itself down, closing the context does nothing more and does not fail.

    Shutdown timeout

    spring:
  actor:
    shutdown:
      timeout: 20s   # default

    spring.actor.shutdown.timeout is how long closing the context waits for the actor system to terminate. It takes any Spring Boot duration (15s, 500ms, PT20S). The default is 20s.

    Keep Pekko's own coordinated shutdown phase timeouts (pekko.coordinated-shutdown.phases.<phase>.timeout) shorter than this setting, so the phases that matter for a graceful leave (cluster-leave, cluster-sharding-shutdown-region, cluster-exiting) finish inside the wait.

    When the actor system stops by itself

    If the actor system terminates while the application runs (for example after the split brain resolver downed this node), the Spring context closes and the process exits with status 1, so Kubernetes or systemd restarts it. Set spring.actor.shutdown.exit-process=false to only close the context. Your code can wait for this with SpringActorSystem.whenTerminated().

    Kubernetes: terminationGracePeriodSeconds and the preStop hook

    When Kubernetes stops a pod it runs the preStop hook, then sends SIGTERM, and sends SIGKILL once terminationGracePeriodSeconds has passed since the start, whatever is still running. A pod killed with SIGKILL cannot leave the cluster and is seen as unreachable by the other nodes. So the grace period must cover all three steps:

    terminationGracePeriodSeconds >= preStop sleep
                                 + web server drain (spring.lifecycle.timeout-per-shutdown-phase)
                                 + spring.actor.shutdown.timeout
                                 + a few seconds margin

    A preStop sleep gives the readiness probe time to fail and the load balancer time to stop sending traffic before the application begins to shut down:

    spec:
  terminationGracePeriodSeconds: 45
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 10"]

    With matching application settings:

    server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 10s   # web server drain
  actor:
    shutdown:
      timeout: 20s                    # actor system coordinated shutdown
    pekko:
      coordinated-shutdown:
        phases:
          cluster-leave:
            timeout: 10s
          cluster-sharding-shutdown-region:
            timeout: 10s

    Here the worst case is 10s (preStop) + 10s (web drain) + 20s (actor system) = 40s, inside the 45s grace period. If you must keep terminationGracePeriodSeconds: 30 with a 10s preStop sleep, lower spring.actor.shutdown.timeout (for example to 15s) and the web drain timeout so the sum stays under 30s.

    Health checks

    With Spring Boot Actuator on the classpath, /actuator/health gets these components:

    Component When Status
    actorSystem always UP while the actor system runs, DOWN once it has terminated. Details: the system's name.
    actorCluster spring.actor.provider=cluster UP when this node is an Up member; OUT_OF_SERVICE while it has not joined yet, is joining, weakly up, leaving or shutting down; DOWN when it was downed or removed, or other members report it unreachable
    actorWarmup spring.actor.provider=cluster UP when this node is an Up member, the cluster has at least management.health.actor.warmup.min-members (default 1) Up members, and the discovery store answers (with jdbc or redis discovery); OUT_OF_SERVICE otherwise

    actorCluster details hold this node's status (selfStatus, NOT_JOINED before it joins), whether it is unreachable (selfUnreachable), the member count (members) and the unreachable count (unreachable), never addresses. An unreachable peer shows only in the count: one partitioned peer does not make every node unhealthy. actorWarmup details hold selfUp, upMembers, minMembers and discovery (REACHABLE, UNREACHABLE or NOT_USED). management.health.actor.enabled=false turns all of them off.

    Neither is in the Kubernetes probe groups by default. Add actorCluster to readiness, so a pod gets traffic only once it is a cluster member and stops getting it as soon as it leaves:

    management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState,actorCluster

    Keep it out of liveness: a node that is still joining is not broken, and restarting it would only delay the join. Cluster Bootstrap reaches pods through Pekko Management, not through the readiness-gated Service, so a cluster still forms while no pod is ready yet.

    Actuator on its own port

    Actuator's endpoints (/actuator/health, /actuator/metrics, /actuator/prometheus, /actuator/info) tell anyone who can call them about the application. Serve them on a separate port, so the network can open the application port to clients and the Actuator port only to monitoring and the kubelet:

    server:
  port: 8080          # application traffic
management:
  server:
    port: 8081        # Actuator: probes and Prometheus

    Point the probes, the ServiceMonitor or PodMonitor and any prometheus.io/port annotation at 8081, and let a NetworkPolicy admit 8081 only from the monitoring namespace. The kubelet's probes come from the node, which most network plugins let through whatever the policy says; if yours doesn't, add an ipBlock for the node addresses on 8081. The Kubernetes example does all of this.

    Warm-up

    In cluster mode the starter adds a third health group beside Spring Boot's liveness and readiness: warmup (/actuator/health/warmup), with the actorWarmup component. It answers "can this node be activated?", which a delivery pipeline asks before it switches traffic to a new deployment (Blue-green):

    Group Question Who asks Depends on traffic
    liveness Restart this pod? kubelet no
    readiness Send this pod traffic? the Service yes
    warmup Is this pod ready to be activated? the delivery pipeline no

    Set min-members to the number of members a new deployment must have before it takes traffic:

    management:
  health:
    actor:
      warmup:
        min-members: 2

    Like actorCluster, keep actorWarmup out of liveness. A group named warmup in management.endpoint.health.group replaces the starter's. The group shows components and details as the main health endpoint does (management.endpoint.health.show-details).

    Production checklist

    Go through this list before the first release of a clustered application.

    Cluster formation and downing

    • [ ] Every node uses the same spring.actor.name.
    • [ ] Nodes find each other through seed-nodes or join: discovery, not join-self (Cluster Formation).
    • [ ] A downing strategy is set. With join: discovery the default is keep-majority; with seed nodes the default is none and the starter logs a warning (Split Brain and Leases).
    • [ ] If a singleton or a shard must never run on two nodes at once, it uses a lease (singleton.use-lease, sharding.use-lease).
    • [ ] The network lets pods reach each other on the remoting port (25520 by default) and the Pekko Management port. The Kubernetes example lists the rules to ask for.
    • [ ] With jdbc or redis discovery or leases, only the nodes can write the store: a dedicated Redis ACL user or database user, TLS and auth (Securing the discovery store).

    Messages

    • [ ] Every message that crosses nodes (sharded commands, replies, topic messages) implements JsonSerializable or CborSerializable. The Kubernetes example also sets spring.actor.pekko.actor.allow-java-serialization: off.
    • [ ] Message changes stay readable by the previous version during a rolling or canary release (Message compatibility).

    Shutdown

    • [ ] server.shutdown: graceful is set.
    • [ ] terminationGracePeriodSeconds covers the preStop sleep, the web drain and spring.actor.shutdown.timeout (above).
    • [ ] spring.actor.shutdown.exit-process stays true, so a downed node restarts.

    Health and monitoring

    • [ ] The readiness group includes actorCluster; liveness does not.
    • [ ] Actuator runs on its own port (management.server.port), open only to monitoring and the kubelet (above).
    • [ ] actor-metrics is on the classpath and Prometheus scrapes /actuator/prometheus.
    • [ ] The dashboard and alert rules from monitoring/ are installed (Monitoring).
    • [ ] spring.actor.metrics.path-tag-limit stays 0, or is small, so the series count does not grow with the number of actors.

    Data

    • [ ] With actor-jdbc or actor-persistence, initialize-schema is never and the tables come from your Flyway or Liquibase migrations (Configuration Reference).
    • [ ] State that must survive a restart or a blue-green switch lives in a database or event journal, not only in actor memory.

    Blocking work

    • [ ] Actors that call blocking I/O (JDBC, blocking HTTP clients) run on withBlockingDispatcher() or a dispatcher of their own (Dispatchers).

    Native images (GraalVM)

    Experimental

    No native image of an actor application has been built and run in this project yet. The Native image workflow (.github/workflows/native-image.yml) builds the simple example every week. Until it passes, treat native images as experimental.

    Spring AOT reads META-INF/spring/aot.factories during a native build. The starter's modules use it to register these runtime hints:

    • Pekko's configuration files: every reference.conf, plus the version.conf and pekko-http-version.conf they include, and your application.conf if you have one.
    • The starter's classes that Pekko creates by name from configuration: the executor of a bean-backed dispatcher, the cluster discovery and lease adapters, the serializer for traced messages, and the persistence database provider. Also the Pekko Jackson serializers the starter configures.
    • AskCommand's reply address, which Jackson writes into every ask that crosses nodes.
    • The schema files of actor-jdbc, actor-persistence and actor-projection.

    Your message classes

    Jackson reads and writes your messages by reflection whenever Pekko serializes them. That covers messages that cross nodes (sharded commands, replies, topic messages) and the events and state of event-sourced actors. Pekko writes each message's class name into the serialized form and loads the class by that name when it reads the message, so register every concrete message class, not only the JsonSerializable interface. @RegisterReflectionForBinding on a configuration class registers each class with its constructors, fields and property types:

    @Configuration
@RegisterReflectionForBinding({HelloActor.SayHello.class, OrderPlaced.class})
public class NativeHintsConfiguration {}

    @Configuration
@RegisterReflectionForBinding(HelloActor.SayHello::class, OrderPlaced::class)
class NativeHintsConfiguration

    Messages between actors in one JVM aren't serialized (Pekko's serialize-messages is off by default), so they need no hints. To register classes you can't list in an annotation, write a RuntimeHintsRegistrar and import it with @ImportRuntimeHints.

    Pekko's own classes

    Pekko 1.1 ships no native image metadata. It creates its extensions, mailboxes, serializers, loggers and actor ref providers by reflection, from the class names in its reference.conf, and the starter's hints don't cover them. One way to collect them is the GraalVM tracing agent. Run the application and its tests on the JVM with -agentlib:native-image-agent=config-output-dir=src/main/resources/META-INF/native-image/<group>/<artifact>, use the features you need (cluster, sharding, persistence), and check in the generated files.

    The actor-metrics Java agent (-javaagent:actor-metrics-<version>-agent.jar) can't attach to a native image.
